# Экспериментальный групповой exit-процесс

Этот режим — кандидат для нагрузочных испытаний, не замена проверенному
одно-профильному менеджеру по умолчанию. Проверка 500 активных клиентов не
проводилась. Формат Session и ключи совместимы с текущим Android-клиентом;
переустановка APK для включения групп сама по себе не нужна.

## Что меняется

- Один процесс допускает до 64 профилей. Рекомендуемый начальный размер
  тестовой группы — 8. Каждый профиль сохраняет собственный секрет, Session,
  документы, cookies, лимиты потоков и скорости.
- IP-стек создаётся при первом валидном пакете. Через пять минут простоя он
  освобождается, если нет активных TCP/UDP-потоков. Каналы к провайдеру при
  этом остаются открытыми: экономия не равна исчезновению всех расходов профиля.
- Входная очередь профиля ограничена 128 пакетами и 256 КиБ, очередь батчей —
  256 КиБ на канал, очередь провайдера — 16 элементами. Текущий отправляемый
  батч, буферы провайдера, Session и сокетов учитываются отдельно от этих лимитов.
- Запуск не более двух профилей одновременно снижает пиковую нагрузку.
  Результат scrypt переиспользуется между каналами одной Session, но не между
  пользователями. Сила KDF, разделение ключей и формат шифрования не меняются.
- Данные статистики записываются атомарно в закрытый JSON, без токенов и
  ссылок документов. Финальные счётчики эпохи хранятся до подтверждения
  менеджером записи в БД. Без подтверждений новые запуски приостанавливаются;
  уже работающие профили не отключаются только из-за заполнения этого журнала.
- При смене подтверждённой Session закрываются старые TCP/UDP-потоки;
  пакеты предыдущей эпохи отбрасываются. Метрики `sessionResets` и `staleDrops`
  показывают пересоздания стека и отброшенные устаревшие данные.

Изоляция памяти теперь имеет гранулярность **группы**, а не одного профиля:
OOM или авария процесса затронет всех его участников. Нельзя объединять
сотни профилей в один неограниченный процесс. У профилей остаются отдельные
IP-стеки; пересечение виртуальных адресов не объединяет их соединения.

## Контракт управления

```text
paperflux --exit-node --session --mode proxy \
  --exit-profiles /private/group/manifest.json \
  --exit-stats /private/group/metrics.json \
  --exit-cookies /private/group/cookies
```

Manifest версии 1 содержит `validUntil` (Unix-время), `profiles` и необязательный
массив `acknowledged` с идентификаторами уже учтённых завершённых эпох.
Профиль: `id`, `token`, `clientIp`, `transport`, `documents`.
Разрешены Yandex Disk (один или два документа) и Mail.ru (один документ).
Для профиля Яндекса допускается `volgaUrl` — отдельный пустой документ
с правом редактирования для резервного Volga-канала.
Нельзя назначать один документ или ключ разным профилям.

Manifest должен быть обычным приватным файлом, не более 256 КиБ;
на Linux — без прав для группы и остальных. Cookies — в каталоге 0700.
Менеджер выдаёт разрешение на 90 секунд и обновляет его каждые пять секунд.
Просрочка отзывает профили даже при неисправном менеджере. Некорректный
новый файл не продлевает старое разрешение. Неизменные параметры не
перезапускают профиль. Переназначение документа ждёт завершения старого.

Служебные порты пока сохранены по схеме `24000 + ID`. Общий авторизационный
listener и автоматическая миграция живых TCP-соединений **не реализованы**.
Это также не механизм совместного использования одного документа всеми клиентами.

## Менеджер и безопасное испытание

Управляющий сервис не входит в публичное native-ядро. Он должен закреплять
профиль за группой, обновлять manifest и учитывать статистику без дублирования
завершённых эпох. Удаление соседа не должно перемещать работающие профили.
Одновременная работа двух менеджеров на одних документах запрещена.
В тестовой версии `PAPERFLUX_GROUP_COOKIE_DIR` задаёт общий приватный каталог
cookies и Linux-блокировок профилей. При одинаковом каталоге две группы не
запустят один профиль одновременно. `PAPERFLUX_GROUP_START_LOCK_DIR` задаёт
общий приватный каталог для ограничения дорогого старта двумя профилями
на все группы. Оба каталога должны принадлежать пользователю процесса;
их нельзя использовать между независимыми инсталляциями.
Для Linux/systemd-развёртывания с делегированными cgroup v2 используйте
`KillMode=control-group`, `UMask=0077`, `Delegate=cpu memory pids`.

Ограничения памяти и числа задач в этом режиме должны охватывать целую
группу. Старый бюджет одного worker нельзя считать
автоматически достаточным для восьми активных профилей. Общий `MemoryMax`,
CPUQuota, лимит файлов и число групп выбираются по доступным ресурсам;
соседние VPN/боты не должны включаться в эту cgroup или перенастраиваться.

Перед включением на общедоступном узле нужны:

1. Сравнение старого и группового процессов на отдельных тестовых документах,
   без второго экземпляра на документах работающих пользователей.
2. Нагрузка через реальные Yandex/Mail.ru: 8, затем 16 активных профилей,
   включая DNS, большие загрузки, короткие запросы, обрывы и повторный запуск.
3. Измерение RSS/cgroup memory, CPU, p95 задержки, полезной скорости,
   заполнения очередей, ошибок и повторов; длительный тест стабильности.
4. Проверка месячной квоты, остановки профиля, восстановления после аварии
   менеджера и процесса. Авария native между публикациями статистики может
   потерять до интервала публикации (пять секунд) счётчиков; строгий биллинг
   требует дополнительного устойчивого журнала или внешнего учёта.
5. Тест с race detector на Linux. Обычные unit/integration-тесты
   не заменяют проверку конкурентного доступа.

Ограничение Мбит/с сейчас фиксированное на профиль, а не планировщик с
заимствованием свободной полосы. Вместимость пула определяется измерениями
и ограничениями провайдеров, а не размером группы или числом строк в БД.
