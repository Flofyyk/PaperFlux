# PaperFlux Server

**Русский** · [English](README.en.md) · [Android-клиент](https://github.com/Flofyyk/PaperFluxAndroid) · [Развёртывание](docs/DEPLOYMENT.md)

PaperFlux — TCP-туннель с передачей данных через Yandex Docs. Клиент принимает трафик приложений, а сервер на VPS доставляет его до адресата и возвращает ответы по тому же каналу.

Проект основан на [OpenFlux](https://github.com/p1neappleXpress/OpenFlux). Этот репозиторий содержит сервер и общее транспортное ядро PaperFlux; Android-приложение находится в отдельном репозитории.

## Как это работает

```text
Приложения на Android
        ↕
VPN-интерфейс → обработка TCP
        ↕
Шифрованная Session / PFS2 (совместимый режим)
        ↕
Yandex Docs — канал совместного редактирования
        ↕
Расшифрование на VPS
        ↕
TCP-узел PaperFlux → целевой сервер
```

**Приём трафика.** Android-клиент создаёт системный VPN-интерфейс. Пакеты из него обрабатываются локальным сетевым стеком и передаются в TCP-туннель. Для десктопного режима предусмотрен вход через SOCKS5.

**Передача через документ.** Клиент и VPS подключаются к одному документу Yandex Docs. Транспорт использует служебные сообщения курсора в канале совместного редактирования: данные упаковываются в батчи, шифруются и кодируются для передачи внутри сообщений Socket.IO поверх Engine.IO/WebSocket. Для этой передачи не требуется записывать содержимое пакетов в текст документа.

**Выход в интернет.** VPS извлекает данные из сообщений и передаёт TCP-потоки целевому серверу. Ответы проходят обратный путь до приложения. Доступны два серверных режима: `proxy` открывает обычные исходящие TCP-соединения и не требует root; `raw` сохраняет пакетный режим и требует системной настройки Linux.

## Возможности

- Зашифрованный транспорт между Android-клиентом и VPS с отдельным секретом для каждого профиля.
- Один или два документа в профиле: второй канал служит резервом, если первый временно недоступен.
- Автоматическое восстановление сессии после обрыва и проверка DNS/TCP перед статусом «подключено».
- Контроль очереди: устаревшие данные не отправляются после долгой потери связи.
- Два режима выхода на сервере: `proxy` без root и `raw` для пакетного режима Linux.

## Защищённая сессия

Профиль связывает клиента и сервер общими параметрами: идентификатором, секретом и документом. Новая Session согласует возможности сторон, шифрует сообщения AES-256-GCM с отдельными направлениями и объединяет доступные каналы в одну сессию. До подтверждения защищённой сессии пользовательские данные не принимаются. PFS2 с X25519 сохранён как отдельный совместимый режим; смешивать его с Session нельзя.

Шифрование действует между клиентом и VPS. Дальнейшая защита соединения с сайтом зависит от протокола приложения, например HTTPS. Сервис документа может наблюдать время, размер и частоту сообщений. Подробности: [PFS2](docs/SECURITY_PFS2.md).

## Соединение и восстановление

Подключение проходит три этапа: авторизация документа, установление защищённой сессии и проверка DNS/TCP через выходной узел. Успешного подключения WebSocket недостаточно для подтверждения работы всего туннеля.

При обрыве транспорт повторно получает параметры документа и создаёт новую WebSocket-сессию с новым идентификатором участника. После работавшего соединения предусмотрена одна быстрая повторная попытка; последовательные ошибки используют возрастающую задержку со случайной добавкой, не более 30 секунд. Транспорт завершает собственную блокировку совместной авторизации редактора без сохранения или изменения содержимого документа. Пакеты имеют ограниченный срок хранения в очереди: устаревшие данные не отправляются после длительного обрыва.

Профиль может содержать один или два документа. При двух документах новый TCP-поток закрепляется за одним готовым каналом, поэтому пакеты одного соединения не перемешиваются между документами. Если один канал временно недоступен, второй продолжает обслуживать туннель, а закрывшийся восстанавливается отдельно.

При перезапуске exit-node клиент повторно обнаруживает сервер, не ожидая окончания старого peer-таймаута. Замена защищённой сессии требует ответа на свежий challenge: запоздавшие ответы предыдущей сессии не подтверждают новую. После возвращения документного канала Android сразу проверяет DNS/TCP, не пересоздавая VPN без необходимости.

## Совместимость

Доступны `yandex` (один или два документа), `vyandex` (редактор Volga), `cupsonline` и `mailru`. Клиент и сервер должны использовать один транспорт и одинаковые параметры профиля. Новый формат Cups требует обновления обеих сторон.

Volga выбирается отдельно: этот режим записывает операции в документ, поэтому для него нужен отдельный пустой документ с доступом на редактирование. Существующие профили Yandex Docs автоматически на Volga не переводятся. [Параметры транспортов и проверка Яндекса](docs/TRANSPORTS.md).

Основной сценарий — PaperFlux Android и сервер PaperFlux с транспортом Yandex Docs. Режим `proxy` обрабатывает IPv4 TCP и UDP через обычные исходящие сокеты; IPv6 не поддерживается. Используйте клиент и сервер с одним протоколом: Session либо PFS2. Для серверной CAPTCHA доступен отдельный шифрованный служебный канал, не передающий обычный VPN-трафик; настройка описана в [параметрах транспортов](docs/TRANSPORTS.md).

PaperFlux Server 0.5.6–0.5.8 и Android 0.4.14–0.4.16 используют совместимый протокол Session. Для сервера укажите `--session`. Старый PFS2 доступен без этого флага только для совместимых старых клиентов. Добавление по адресу и ключу требует отдельного сервиса конфигурации; импорт полных профилей работает без него.

В 0.5.8 при смене подтверждённой клиентской сессии групповой `proxy` закрывает старые TCP/UDP-потоки и пересоздаёт сетевой стек. Запоздавшие пакеты и ответы предыдущей сессии отбрасываются. Обычная ротация документа не сбрасывает работающие потоки. Это устраняет накопление устаревших соединений при переподключении; формат Session не меняется.

## Готовые сборки

В [последнем релизе](https://github.com/Flofyyk/PaperFlux/releases/latest) доступны Linux-бинарники `amd64` и `arm64`. Для большинства VPS нужен `amd64`; для ARM-серверов — `arm64`. Архитектуру можно проверить командой `uname -m`: `x86_64` соответствует `amd64`, `aarch64` — `arm64`. Настройка профиля и сервиса описана в [инструкции развёртывания](docs/DEPLOYMENT.md).

## Документация
